# Documentation site — plan

A documentation site for hagrid, built with Astro Starlight, living in this repo alongside the
library.

## Goals

- One page per technique, each with a live interactive example.
- API reference generated from the TSDoc comments already in `src/`, so it cannot drift.
- Versioned docs, so `0.1.x` users are not shown `0.2.x` behaviour (the API changed — see
  *Migrating from 0.1.x* in `README.md`).
- A reproduction page for the evaluation results.
- Machine-readable output for LLMs.

## Tech stack

| concern | choice | notes |
| ---- | ---- | ---- |
| site | [Astro Starlight](https://starlight.astro.build) | |
| API reference | [`starlight-typedoc`](https://github.com/HiDeoo/starlight-typedoc) | driven off `src/main.ts` and `tsconfig.json` |

| LLM output | [`starlight-llms-txt`](https://github.com/delucis/starlight-llms-txt) | emits `/llms.txt`, `/llms-full.txt` |

`docs/` depends on the library via a workspace link (`pnpm-workspace.yaml` at the repo root), so the
examples exercise the real build rather than a copy.

## Phases

### 1. Scaffold

- Add `pnpm-workspace.yaml`; move the library into the workspace root or keep it at root and add
  `docs` as the only extra package.
- `pnpm create astro@latest docs -- --template starlight`.
- Add `@astrojs/svelte`, `starlight-typedoc`/`typedoc`, `starlight-versions`,
  `starlight-llms-txt`.
- Root scripts: `docs:dev`, `docs:build`. Wire `docs:build` into CI so a broken link or a
  TypeDoc failure fails the build.
- Decide the deploy target and base path (see *Open questions*).

**Done when:** `pnpm docs:dev` serves a Starlight site with a working generated API section.

### 2. Interactive example component

Everything in phase 3 rides on one component, so build it once, properly.

- `Scatterplot.svelte` — canvas, draws points before/after, ports what
  `SiGrid/presentation/src/lib/components/ScatterplotCanvas.svelte` already does.
- `GridDemo.svelte` — wraps it with: dataset picker, method parameters as controls, a
  before/after toggle or side-by-side, and a readout of `runtime` and cells-per-point.
- Datasets: three or four small CSVs in `public/data/`, chosen to show the failure modes the
  README documents — a square set, an elongated set (1000x10), a quantised/lattice set, one with
  duplicates. Sourced from `SiGrid/evaluation/data/`.
- `cmds` needs a different driver: it yields a generator, so the demo steps it under
  `requestAnimationFrame` and animates the optimisation. Build this as a variant of `GridDemo`, not
  a special case inside it.

**Done when:** one page renders the component and switching parameters relayouts live.

#### Drawing the layouts correctly

Two bugs cost real debugging time in the playground, and both look like library faults when you
hit them. Get these right in `Scatterplot.svelte` once and every page inherits it.

**1. Methods do not all answer in the same coordinate space.**

| method | output |
| ---- | ---- |
| `gosper`, `nmap`, `cmds` | the input's own coordinate space |
| `hilbert`, `gilbert`, `dgrid` | grid indices on a `cols × rows` lattice |
| `gridfit` | grid units, and it must be *given* grid units |

So the original points and the layout are only sometimes in the same space. The tempting thing —
normalise each by its own bounding box so both fill the canvas — silently invents displacement,
because the two bounding boxes differ. Measured on clustered gosper output it shifted every point
by a **median of 1.67 cell pitches, worst 3.00**: enough that an outlier appears to sit in empty
space several cells from the hexagon it was actually placed in, with a long connector implying a
bug that is not there.

**Project the originals into the method's output space, then use one transform for both.** For the
first row that is the identity. For the lattice methods, scale the bounding box onto
`[0, cols-1] × [0, rows-1]`, one axis at a time — which is what they do internally before rounding,
so what remains on screen is real displacement:

```js
const bb = get_bounds(data);
const sx = bb.width  > 0 ? (cols - 1) / bb.width  : 0;
const sy = bb.height > 0 ? (rows - 1) / bb.height : 0;
const source = data.map(([x, y]) => [(x - bb.x) * sx, (y - bb.y) * sy]);
```

with the lattice taken from the method: `hilbert` is `2^level` square (its per-axis scaling is
where the squashing of non-square data comes from); `gilbert` is `gilbert_dimensions(...)` or the
explicit `width`/`height`; `dgrid` is `rows = max(1, floor(sqrt(N · aspect_ratio)))`,
`cols = ceil(N / rows)`. Note `dgrid` assigns by rank rather than by an affine, so for it this is a
fair reference frame rather than an exact preimage — say so in the caption.

**2. A background grid must be anchored to a cell, not to the canvas.**

Stepping grid lines from the viewport origin leaves the lattice floating by an arbitrary fraction
of a cell, so occupied cells look mis-seated and empty ones look available when they are not.
Anchor to a known cell *boundary* and step by the pitch:

- integer-lattice methods put centres on integers, so boundaries are the half-integers
- `cmds` snaps to `(k + ½)·size`, so boundaries are the multiples of `size`
- hexagons have no axis-aligned lattice: draw them per cell from `gosper_decode`, never by stepping

Whatever formula picks the level or the grid dimensions must match `gridify`'s exactly, or the grid
you draw is not the grid the points were placed on.

**Regression check.** Take a point that did not move — an isolated one, or any point on a run where
no cell was contested — and assert its drawn position equals its cell's drawn position to within a
pixel. Both bugs above make that fail; nothing else does.

### 3. Technique pages

One page each, same shape throughout: what it does → parameters → live demo → when it fails →
reference link.

- `hilbert` — square power-of-two grid; note the duplicate-point collision caveat.
- `gilbert` — arbitrary aspect ratio; the elongated-data comparison table from the README is the
  demo's whole point.
- `gosper` — hexagonal; `orientation` toggle in the demo, `-1` outside the island.
- `dgrid` — fills the area at a given cell aspect ratio.
- `cmds` — animated; state plainly that it is the least trustworthy method here.
- `nmap` — treemap; demo the degenerate-axis throw with the lattice dataset, and show
  `nmap_regions` drawn as rectangles. Cover `squared` and what it does *not* promise.
- `gridfit` — grid-cell-unit input; the robust one for awkward data.

Most of the prose already exists in `README.md` — the per-method sections there are the source
material, not something to rewrite from scratch. Trim `README.md` to an overview plus a link once
the site is up, so there is one copy of each claim.

**Done when:** all seven pages exist with a working demo, and `README.md` no longer duplicates them.

### 5. Evaluation reproduction page

The existing pipeline in `SiGrid/evaluation/` is a four-stage chain over ~N CSVs in `data/`:

| stage | script | output |
| ---- | ---- | ---- |
| layout | `0010_compute_grids.js` | `results_grid/result_*.json`, `results.json` |
| metrics | `0020_compute_metrics.js` | `results_with_metrics.json` |
| compaction | `0030_compact.js` | `results_compact.json` |
| statistics | `0040_statistics.js` | `statistics.json`, `all_statistics.json` |

Metrics: trustworthiness (k = 5% of N) and CC via `sickle`, orthogonal ordering via
`util/orthogonal_ordering.js`, plus `duration` and `collisions`. Statistics are binned by dataset
size, reported as mean/stdev/median/quartiles with Tukey fences and outliers.

**This does not transfer as-is.** That pipeline compares SiGrid variants against hagrid and DGrid;
a hagrid docs page should compare *hagrid's own seven methods* against each other. So:

- Port the pipeline into `evaluation/` in this repo, keeping the stage numbering and the metric
  definitions, but swapping the technique list for hagrid's methods.
- Keep it a committed, runnable script set — the page is a reproduction page, so the commands on it
  have to be the commands that produced the numbers.
- Commit `statistics.json` / `all_statistics.json` (small) into `docs/public/`; do **not** commit
  the raw per-file results.
- The page: methodology, the datasets and where they came from, the metric definitions, the exact
  commands, and the results rendered as Svelte box plots (port `Table.svelte` from the SiGrid
  presentation).
- Record the environment the numbers were measured on, and note that `duration` is machine-dependent.

**Done when:** running the documented commands from a clean checkout reproduces the committed
statistics files.

### 6. Versioning, LLM output, deploy

- Cut the first version snapshot at the *current* release, so `0.2.0` is archived before `0.3.0`
  work lands. Decide whether `0.1.x` gets a hand-written stub or nothing at all.
- Configure `starlight-llms-txt` — set the site description, and exclude the generated API pages
  from `llms-full.txt` if it bloats past usefulness.
- Deploy, and add the URL to `package.json` (`homepage` currently points at `renecutura.eu`).

## Open questions

1. **Deploy target** — GitHub Pages under `saehm.github.io/hagrid`, or a subdomain of
   `renecutura.eu`? Determines `site` and `base` in the Astro config.
2. **Repo or separate** — plan above assumes `docs/` in this repo. Alternative is its own repo;
   in-repo is better for keeping the API reference honest.
3. **Evaluation scope** — port the pipeline to compare hagrid's methods (my recommendation, above),
   or just present the SiGrid numbers as-is with hagrid as one row?
4. **Dataset licensing** — the SiGrid `data/` CSVs are derived from public datasets (abalone,
   boston, breast, caltech, MNIST, …). Which can be redistributed in a public docs site?
5. **`0.1.x` docs** — worth writing, or is the migration guide enough?

## Explicitly out of scope

- Benchmarks as a CI gate. The performance numbers in `README.md` are measurements, not thresholds.
- A playground that accepts arbitrary uploaded data. Fixed sample datasets first.
